UX_STREAMLINING.md — Making the Ensemble Disappear

Status: research + prioritized opportunity catalog, 2026-04-24. Author: Kevin (direction) + Maestro (synthesis). Goal (Kevin’s words): “streamline user consciousness and make inputs disappear… manage agents effectively… elevate the project’s goal of efficiency overall and improved UX with Claude.” Audience: future self-Kevin + any Virtuoso/Agent planning UX work.

0. What we’re trying to achieve

Three levers, in order of leverage:

  1. Invisible inputs. The Agent should act on what it can already infer — cwd, time of day, recent activity, pending work. Kevin should only be asked about genuine forks, not about sub-steps.
  2. Ambient status. Kevin should see the Ensemble’s health without checking. A glance at the menu bar, the phone, the desk — not a status command.
  3. Push, don’t pull. When attention is genuinely needed, the Ensemble reaches out (notification, iMessage, Pushover). Kevin doesn’t hunt for state.

The anti-goal is automation so aggressive it loses control. Decisions that actually matter — scope, architecture, launch — stay in Kevin’s hands. Everything else is friction we remove.

1. Current friction audit — where Kevin clicks or types the most today

Ranked by observed frequency:

Friction Estimated clicks/turn Cause
“Where am I in this project?” Every session start No per-agent dashboard; must ask chat or read status file manually
“What did autopilot do last night?” Every morning No consolidated view; must tail logs or open Maestro chat
Answering AskUserQuestion for sub-steps Several per hour Some Agents still interrupt for sub-steps; the batching memory is new
Firing autopilot for a specific project Every phone trigger Requires knowing the slug; Termius snippets hardcode it per-button
Running status / brief / checking run logs Daily+ No always-visible health surface
Typing in Claude Code chat vs voice Every instruction No voice input wired up (Mac has Dictation; unused for Claude)
Deciding which Agent to use Per task No contextual dispatch — Kevin picks the chat

Total cost: rough estimate ~40–80 button clicks / key presses per productive hour that exist only to surface state or route requests — pure interaction tax, not decision-making.

2. Opportunity catalog (12 items, prioritized)

Each opportunity: what it is · how it helps · rough effort · existing-tool basis.

P0 — highest leverage, lowest effort (do first)

A. Menu bar app — always-visible Ensemble health

What: A tiny macOS menu-bar icon (SwiftUI MenuBarExtra or Swift + AppKit, ~200 lines) that polls state.json + chats/*.json every 30 sec. Shows: - 🟢 / 🟡 / 🔴 overall health (mode, lock state, any pending attention) - Count of unreviewed [autopilot] commits across all repos - Last autopilot run timestamp + project - Click → dropdown with quick actions: fire autopilot per project, open latest run log, view status.

How it helps: Kevin sees state in his peripheral vision. Zero clicks to check health. Status commands retire. Effort: 1 focused day in Xcode. Tailor via SwiftUI MenuBarExtra (native since macOS 13). No App Store submission — unsigned .app with xattr -d com.apple.quarantine. Basis: Ice / Bartender / Xbar / SwiftBar — any “read JSON + render” menubar utility.

B. Context-sensitive /autopilot slash command

What: Claude Code skill /ensemble:autopilot N that reads the current chat’s cwd, infers which project it’s in (via chats/*.json repo_path match), and fires autopilot against THAT project without Kevin specifying.

How it helps: In a BOO chat, /autopilot 30 fires BOO. In Vera Nota, fires Vera Nota. No project slug typing. Effort: 1-line extension to mobile_dispatch.sh (already supports project arg) + a .claude/commands/autopilot.md skill file with a small bash wrapper. ~30 min. Basis: Claude Code’s custom slash command pattern.

C. Push notifications to phone (not just Mac-local)

What: When autopilot fires / finishes / needs attention, the Ensemble pushes to Kevin’s Android via Pushover (free tier, 10k notifications/month). Replace or supplement the current Mac-local osascript notifications.

How it helps: Kevin knows state changes without looking at his Mac. Phone on desk = ambient status. Effort: Pushover app install on Android (one-time, free). Pushover API: curl -F 'token=' -F 'user=' -F 'message='. Add to autopilot_session.sh post-flight + mobile_dispatch.sh for key events. ~20 min. Basis: Pushover — battle-tested, cheap, integrates with basically anything.

D. Morning digest — one page, overnight in one glance

What: The existing orchestrator-morning-briefing scheduled task writes a daily briefings/YYYY-MM-DD.md but Kevin has to go find it. Enhance: also write a single briefings/today.html that covers: - Overnight autopilot runs: project, duration, commits landed, diff summary - Any Agent’s needs_attention = true flag raised - Cross-project top rec: the single thing worth doing first today - Tail of launchd-consumer.log for any errors

HTML is served locally by python3 -m http.server or pushed to the ensemble-phone repo’s GitHub Pages at /brief.html.

How it helps: Kevin opens a bookmark, sees yesterday + this morning in one scroll. Effort: ~2 hr. Mostly bash + python for the report generator; HTML template reused from ensemble-phone visual system. Basis: existing morning-briefing routine; the bin/status.sh + new report builder.

P1 — meaningful impact, moderate effort

E. Review queue web view

What: A locally-hosted (or Pages-hosted, via private-URL) page that lists all unreviewed [autopilot] commits across all project repos, each with: project, commit hash, one-line summary, diff preview (via git show --stat), buttons to approve (mark reviewed) or revert.

How it helps: Autopilot runs overnight. Kevin triages in 5 min over coffee instead of cd-ing into each repo. Effort: ~1 day. Bash script walks repos, extracts [autopilot] commits since last marker, writes JSON + renders HTML. No backend needed; click handlers can shell out via a small local HTTP helper. Basis: same pattern as the morning digest.

F. Voice input via macOS Dictation → Claude Code

What: Global keyboard shortcut (default Fn Fn) for Dictation is already set. Add a step: build a Shortcut that captures dictated text → sends to Claude Code chat via AppleScript / URL scheme. “Siri, fire 30m on BOO” → Shortcut → mobile_dispatch.sh fire 30 "" boo-website.

How it helps: Hands-free autopilot trigger. Particularly useful mid-task at the Mac. Effort: ~2 hr. macOS Shortcuts + Dictation already native; wiring is glue. Basis: macOS built-ins.

G. Raycast extension for Ensemble

What: Raycast (free, Mac power-user launcher) supports custom extensions. Build an “Ensemble” extension with commands: ens status, ens fire boo 30, ens read latest run, ens kill, ens open phone cheat sheet. Raycast’s fuzzy-match means Kevin types ef b 30 for “ensemble fire boo 30.”

How it helps: Cmd-Space → type 3 chars → fire autopilot. No Terminal, no Claude Code chat, no phone. Effort: ~4 hr. Raycast extensions are TypeScript + their SDK. Thin wrapper around mobile_dispatch.sh. Basis: Raycast extensions API (~2024-mature).

H. Automated agent state summary on Maestro spawn

What: When a Maestro chat spawns (bootstrap), it already reads chats/*.json. Enhance: also pre-compute a one-sentence “what’s changed since last Maestro session” — diff of last_heartbeat timestamps, new entries, needs_attention flags. Surface as the opening line of the rapid-fire report.

How it helps: Maestro’s first response is already context-rich; Kevin skips “catch me up” back-and-forth. Effort: ~30 min. Edit the Maestro bootstrap + add a python helper.

P2 — longer-horizon or bigger surface

I. iMessage reply-to-respond — the Dispatch pattern, self-hosted

What: A persistent iMessage thread to yourself. When Agent needs attention, it sends an iMessage (“BOO autopilot paused at G7 pre-launch — approve push to production? Reply YES or NO.”). Kevin replies. A launchd agent watches the Messages database, parses “YES,” writes the approval to a trigger file, autopilot resumes.

How it helps: Kevin already checks iMessage. No new app, no new UI. Reply from Apple Watch. Effort: ~1 day. Messages DB watcher + parser + trigger writer. Requires Full Disk Access for the watcher process. Basis: macOS Messages SQLite database (~/Library/Messages/chat.db).

J. Contextual autopilot — intent inference

What: Autopilot reads calendar (Google Calendar via MCP), time of day, recent commits across all projects, any needs_attention flags, and autonomously picks project + task when Kevin fires a bare fire 30 without a slug. Rules: - Morning (6–10am): pick project with most needs_attention - Workday (10–4): pick project with most-stale last_heartbeat (least attention recently) - Evening (4–10): pick project with most-recent-commit momentum (keep shipping) - Weekend: pick BOO (personal-project day)

How it helps: Single phone button that figures out what to work on. Effort: ~half day. Rule engine in python; fed by chats/.json and git. Basis:* simple heuristics, not ML.

K. Cross-project commit feed

What: Single git log-style feed merging commits from all onboarded project repos, annotated with project name. Live view or daily digest. Shows velocity, patterns, what autopilot is actually doing.

How it helps: Kevin sees “what Ensemble shipped this week” in one list. Useful for retrospectives. Effort: ~2 hr bash + HTML.

P3 — exploratory / bigger bets

L. iOS native companion app

What: A lightweight Swift app that replaces Termius for Ensemble-specific workflows. Home screen widget showing status; one-tap fire buttons; native iOS notifications; native secure SSH key storage; Apple Watch complication.

How it helps: Premium phone experience. Widget is always-visible status. Effort: 1–2 weeks, plus App Store submission (App Store gated per safety_constraints.md). Maybe ship via TestFlight for personal use only. Basis: Swift + NMSSH library + SwiftUI widget kit.

4. Recommended sequence

  1. Pushover push notifications (C). 20 min. Immediate feedback loop improvement; Kevin knows state changes from anywhere.
  2. Menu bar app (A). 1 day. Ambient health indicator.
  3. Context-sensitive slash command (B). 30 min. Kills “which slug?” friction.
  4. Morning digest HTML page (D). 2 hr. Single scroll for overnight summary.
  5. Maestro-spawn context auto-compute (H). 30 min. First response is always warm.
  6. Evaluate after 1–2 weeks of living with these five. Decide whether P1 items are still valuable.

5. Principles to keep

When building any of these:

  • Never break the kill switch. Every surface must honor bash ~/.claude/orchestrator/bin/mobile_dispatch.sh kill. Global escape hatch.
  • Respect safety_constraints.md. The gated actions (destructive ops, store submissions, deploys beyond Pages, public-flip, billing) stay gated even from cool new UIs.
  • Local-first. State lives in the Mac’s filesystem. UIs read from there. No cloud round-trip for basic operations.
  • Stateless surfaces. The menu bar app, Raycast extension, etc. all render from current state — they don’t accumulate local state that could drift.
  • Throughput > gloss. A rough menu bar icon that works is better than a polished one that doesn’t ship.
  • Undoable actions prefer the phone/chat/Raycast tier; irreversible actions stay in interactive Claude Code chat. Keeps the UX calibrated to reversibility.

6. What this doc is NOT

  • Not a commitment to build any of these. It’s a catalog.
  • Not exhaustive. Other opportunities exist (Slack integration, web-based Maestro chat, multi-user Ensemble) — those are deferred as lower-priority for Kevin’s current solo use.
  • Not a replacement for the Maestro chat + Claude Code as primary interface. These are accelerants, not substitutes.
  • Not a plan for the friend-facing website-agent (that lives in its own lane).
