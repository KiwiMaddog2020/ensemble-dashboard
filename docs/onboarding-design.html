Onboarding Design — The Ensemble

Status: v0.1 draft, 2026-04-22 Locked: phases 1–6 + permissions architecture + tool flexibility + v1 optimizations Next: build v1 per §11 build order Supersedes: nothing (first version)

This document is the single source of truth for the Ensemble installation and onboarding experience — every decision locked across six planning phases, permissions design, tool flexibility patterns, and v1 shipping optimizations.

Goal: someone drops a file structure, a GitHub URL, or a natural-language phrase into Claude Code. The system unravels before their eyes, walks them through every step, and ends with them running the Maestro. Apple-product simplicity, shuttle-grade rigor.

1. Audience and scope

  • v1 audience: Kevin (private preview, personal dogfood); 3–10 invited beta users once v1 is proven; public preview later.
  • v1 platform: macOS only (Darwin). Multi-machine sync and Linux support in v2.
  • v1 interaction surface: Claude Code CLI + Desktop app. Scheduled tasks via mcp__scheduled-tasks__*. Mobile triggers via cloud Routines + iOS Shortcuts + iMessage Channels (Track G).

2. Phase 1 — Entry points

Three paths, one destination

Path A — Canonical paste (primary):

Install The Ensemble from https://github.com/KiwiMaddog2020/claude-ensemble — clone to ~/.claude/orchestrator (back up any existing), then open INSTALL.md and walk me through it.

Path B — URL drop:

https://github.com/KiwiMaddog2020/claude-ensemble

Chat detects the Ensemble repo (README fingerprint), offers install.

Path C — Natural language:

Set up The Ensemble

Chat uses skill discovery (/maestro-install or similar) or asks a clarifying question.

All three funnel to the same bootstrap logic inside INSTALL.md in the repo — one source of truth, always current.

Install location

Default: ~/.claude/orchestrator/. Step 1 asks “Install to default path, or specify a different location?” (2-option AskUserQuestion, default highlighted). Custom paths validated for special characters.

Dry-run mode

Approval gate offers Proceed / Dry-run only / Cancel (3-option). Dry-run runs every read-only check for real (pre-flight, existing-file parses, diff computations) but simulates writes verbally. Successful dry-run ≈ 99% likelihood of successful live-run.

Approval granularity

One bulk approval after pre-flight + plan preview. Chat narrates each step as it executes. Optional extensions (Routines, Mobile, First-Agent) each get a per-extension approval after essentials complete.

3. Phase 2 — Bootstrap flow

Entry sequence

  1. Chat receives paste / URL / natural-language entry.
  2. Runs parallel pre-flight (§10 opt. 1) — all checks concurrent, results collected into one status block: - OS detect (uname -s) - Claude Code version (claude --version) - Dependencies: git, gh, jq, python3 - gh auth status (private repo currently requires it) - Disk free ≥ 1 GB - Existing ~/.claude/orchestrator state - Existing ~/.claude/settings.json validity
  3. Missing dep → offer brew install <dep> via AskUserQuestion. If brew absent, print official install URL, pause, resume on continue.
  4. Print the full 8-step plan with what/how/verify per step.
  5. AskUserQuestion: Proceed / Dry-run only / Cancel.
  6. Execute with per-step narration and checkpoint writes.

The 8 essentials

# Action Verify On failure
1 Back up existing dir if non-empty to ~/.claude/orchestrator.backup.<ts>/ ls -A on target is empty Ask user to confirm overwrite or pick new path
2 git clone repo to install path .git/ exists in install path Retry once; else surface stderr + diagnostic block
3 Write initial state.json (schema v1) jq . state.json passes Surface raw content, ask to inspect manually
4 Copy work_hours.example.json → work_hours.json; offer edit File exists + parses Retry with fresh copy
5 Merge hooks into ~/.claude/settings.json (read → merge → show diff → approve → atomic write) Our hook appears in settings; overall JSON valid If conflict unresolvable: abort with backup path, link TROUBLESHOOTING
6 chmod +x every bin/*.sh test -x each Surface ACL/SIP hints
7 Smoke-test hook: set mode=direct briefly, invoke a trivial MCP tool expected to be blocked, verify block, revert Expected block message visible Dump hook stderr + known-good diagnostic output

4. Phase 3 — Walkthrough UX

Tone

Apple-caliber: clear, declarative, active voice, short sentences, confident. No emojis. No cute humor. No jargon dump. Name what’s about to happen, do it, confirm it. Repeat.

Pacing budget

Essentials total narration ≤ 60 lines. Each step: 1–3 lines of intent, execution, 1-line confirm.

Progressive disclosure

Installation sets up infrastructure only. It does NOT explain Maestro / Agent / Charter concepts. That learning arc happens in the user’s first Maestro session via MAESTRO_BOOTSTRAP.md and the Maestro’s own conversational introduction.

Checkpoint cadence

  • After each essential: ✓ Step N — <one-liner>
  • After all 8 essentials: “Essentials installed. Offer extensions?” (3-option AskUserQuestion: Install now / Review first / Skip)
  • Long steps (smoke test): Testing hook — ~5s…

5. Phase 4 — Pre-mortem

Top 15 install failures (handled inline)

# Failure Detection User message + recovery
1 Repo clone auth fails git clone exit ≠ 0, stderr “authentication” or 403 Pre-flight gh auth status; if fails, link invite flow; else suggest gh auth login
2 Missing dep (jq / gh / python3) command -v empty Offer brew install <dep> via AskUserQuestion
3 Homebrew missing on dep-install command -v brew empty Print install URL, pause, resume on continue
4 Existing non-empty orchestrator/ dir ls -A non-empty Auto-backup w/ timestamp suffix, show path, continue
5 settings.json has conflicting PreToolUse matcher JSON parse + matcher diff Show diff, offer merge-with-priority or abort
6 settings.json invalid JSON jq . settings.json fails Back up corrupt file, write fresh, surface backup path
7 Non-macOS uname -s != Darwin Halt: “v1 is macOS-only; Linux on roadmap”
8 Claude Code version too old for hooks version parse vs min required Link upgrade path, halt
9 Disk < 1 GB free df check Halt with space status, suggest cleanup
10 Ctrl+C mid-install Checkpoint partially populated Next run detects, offers “Resume from step N”
11 chmod didn’t stick test -x after chmod fails Surface sudo/ACL hint, retry
12 Hook smoke test fails Test tool call wasn’t blocked Diagnostic dump: settings contents, script path, jq presence
13 Two installs racing Checkpoint has recent write from other PID Second install stands by, offers takeover if stale
14 Special chars in install path Regex validation Reject, request alternate
15 Sudo invoked whoami == root Halt: “run as your user, not sudo”

TROUBLESHOOTING.md structure

Catalogs the long tail and post-install runtime issues. Sections: - Install failures not in the top 15 - Hooks behaving unexpectedly - Permissions prompts when you don’t expect them - state.json inconsistencies - Routines not firing / firing when they shouldn’t - Channels session drops - Mobile dispatch failures - Recovery from corrupt state

Comprehensive self-test (Step 7 + independent script)

Runs automatically at Step 7 and on demand via bin/self_test.sh. Tests: 1. state.json valid + schema v1 2. All bin/*.sh are executable 3. ~/.claude/settings.json valid JSON 4. Our PreToolUse matcher present 5. Our SessionStart healthcheck present 6. Hook script runs without stderr on a null-input stdin 7. Hook blocks a test tool when mode=direct (temporarily flip, test, revert) 8. If Routines installed: enumerate via MCP, confirm prelude is referenced in each SKILL.md 9. If Channels installed: pgrep -f "claude --channels" finds a live session 10. Scheduled directories (briefings/, queue/, pulse/, runs/) exist and writable

Output: “All systems go.” or a checklist of failures with recovery links to TROUBLESHOOTING.md.

Three shipping optimizations (committed to v1)

  1. Parallel pre-flight — all env checks run concurrently via & + wait, status collected into one block. Saves 2–3s per install.
  2. Dry-run = verification — dry-run runs every read-only operation for real (checks, parses, diffs); simulates writes with narration. If dry-run passes, live-run almost certainly passes.
  3. uninstall.sh — clean removal: strip our hooks from settings.json, archive orchestrator/ to ~/.claude/orchestrator.uninstalled.<ts>/, print restore instructions. Preserves the backup, never deletes user data.

6. Phase 5 — Customization (v1 scope)

  • Single-user, single-Mac is the v1 target.
  • Configurable surfaces: work_hours.json, settings.json allow-list, install path, selected extensions (Routines, Mobile, First-Agent), starter allow-list entries.
  • Brand names locked: Ensemble / Maestro / Agent. Not customizable. Product identity.
  • v2 roadmap:
  • Multi-machine sync via git pull in orchestrator repo + profile export/import
  • Multi-user-on-same-Mac if requested
  • Linux port (remove APFS assumption from lock protocol)

8. Permissions architecture

Session type × permission mode

Session Permission mode Rationale
Interactive Maestro (you at keyboard) default + settings.json allow-list Approvals only for NEW commands; allow-list covers daily drivers
Interactive Agent (you at keyboard) same same
Autopilot (Maestro-spawned, pre-approved) --dangerously-skip-permissions Lock hook still blocks via PreToolUse running before perm check
Scheduled routine (cron-fired) bypass No keyboard; prelude + hook enforce
Channels session (iMessage listener) bypass Remote user can’t click; hook is the firewall
Cloud Routine (Anthropic infra) bypass in cloud No local popups possible

Key safety guarantee

PreToolUse hooks fire before the permission-mode check. Confirmed in Track B research. Even under --dangerously-skip-permissions, our lock hook still blocks VM tools when mode≠orchestrated, lock held by other, or cascade in progress. Bypassing prompts does not bypass safety.

9. Tool flexibility (AskUserQuestion patterns)

Decision shape Options Example
Binary 2 “Back up existing dir?” Yes / No
Split with clear third path 3 “Install jq?” Yes (brew) / No, I’ll do it / Skip
Categorized choices 4 “Install path?” default / custom / detect / other
Combinable (multi-select) 2–4 + multiSelect: true “Extensions to install?” Routines / Mobile / First-Agent
Preview useful any count + preview field “Theme?” Default (shows snippet) / Monospace (shows snippet)
  • Auto-Other always available — tool adds it automatically. Free-text escape hatch.
  • Prefer fewer questions — one sharp decision beats four speculative ones.
  • Paste/attach patterns (natural flow, not a tool feature): when input is complex (existing settings, a charter, a repo README), AskUserQuestion the shape of the decision, then add one plain-text line: “If you have an existing X, paste or attach it in your next message.” User drops content; agent reads and acts.

13. Auto-GitHub extension (optional, first in the post-essentials menu)

Runs immediately after essentials on user approval. High auto-control: the installer runs every gh + git command itself behind one approval gate, narrating each step; user clicks play on the summary command if they want to re-run anything manually.

Creates

  • Private-by-default GitHub repo, name defaulting to <gh-user>/my-ensemble-config (override available). Visibility asked every time — no default — because this repo may contain project names, charters, and personal schedule.
  • Remote push with initial commit.

Tracks (in the user’s config repo, not the canonical Ensemble repo)

File Purpose
work_hours.json Their schedule
allow-list-delta.json Additions beyond the starter allow-list (generated from their settings.json diff)
charters/ Per-project charters, opt-in per project for privacy
version.json {canonical_commit_sha, installed_at, last_synced_at} — pointer to which canonical Ensemble version they’re running
README.md Auto-generated: “Personal Ensemble config for . See github.com/KiwiMaddog2020/claude-ensemble for the system.”

Syncs

  • On-demand: bin/sync-config.sh → git commit -am "auto-sync" && git push
  • Optional nightly cron (offered at setup): commits any deltas every 24 h, skips if nothing changed.

Multi-machine

  • On a new Mac: run the canonical installer first, then git clone <config-repo> ~/.claude/orchestrator-config. A post-clone symlink step wires work_hours.json, allow-list deltas, and charters into place.
  • No sync for state.json / state.lock.d/ / chats/* — those remain runtime-local.

14. Rolling upgrade / canary testing on Kevin’s workspace

Kevin’s existing chats and projects are user-zero — the canary population. Every stable capability ships to him first, gets validated in real use, and only then propagates to invited beta users.

Release channels

Channel Criteria Audience
edge Latest commit on main Kevin only
stable Tagged release after Kevin runs it 3+ days without incident Kevin + private beta invitees
public Tagged release after 3+ beta users run it 7+ days Everyone after public preview

Each Agent’s status.json gets ensemble_version = <git sha> — the commit it was onboarded with. Stale agents are flagged in Maestro’s morning briefing.

Upgrade notification mechanics

  • Morning briefing lists: “Upgrades available — N Agents behind latest by M commits.” Each stale Agent gets a play-button bash snippet to re-run the bootstrap and pick up the new template.
  • On git pull in the orchestrator repo via bin/upgrade.sh, the script prints a summary of what changed and which Agents need re-bootstrapping.
  • /upgrade-agent slash command — any Agent can self-upgrade by re-reading the latest AGENT.md + onboarding_prompt.md without losing its charter or status.

Canary rollout process for a new feature

  1. Feature lands on main (edge channel).
  2. Maestro’s next session surfaces: “New capability: X. Upgrade [list of your Agents]? (Yes / Review first / Skip)”
  3. Kevin approves on Agents where he wants to test.
  4. Agents re-read latest template next session or via /upgrade-agent.
  5. Kevin uses the feature in real work for ≥3 days.
  6. If no problems: tag a stable release; feature becomes default in fresh installs and broadcasts to beta users.
  7. If regressions: Maestro offers bin/rollback.sh <version> to revert specific Agents.

Kevin’s dogfood plan (concrete)

Week Action
1 Self-install the canonical flow; verify hook + lock + state.json work; cold install from scratch
2 Onboard BOO-Website as Agent #1 (it’s already the most Ensemble-shaped of your repos); validate daily

Back-out mechanism

  • Every upgrade writes a snapshot to backups/pre-upgrade-<sha>/
  • bin/rollback.sh <version> restores: template files, settings.json hooks, and broadcasts a downgrade message to affected Agents
  • Rollback is idempotent and always available
