Mission Roadmap — Closing the Ensemble Pitch Gaps

Status: Phase 0 mission gaps 1–4 CLOSED. v2.0 contract sweep shipped 2026-04-26 (eight directives + three-layer mutex + Tier 1/2/3 hardening + SwiftBar indicator). Gap 5 (cross-machine sync) deferred to Phase 2. The pitch is architecturally true rather than aspirational. Phase 0 at ~95%; remaining work is friend hand-off + public-flip (user-action-only).

Original draft 2026-04-25 after honest gap audit. The Ensemble’s primitives (lock, kill-switch, autopilot pipeline) were real and stable; the orchestration layer that the business pitch promises (rotation, code-vs-test semantics, plan→code→test→fix loops) was largely aspirational. This doc enumerates what was needed to make the pitch true, sequenced by dependency, with shipping evidence per gap.

Pitch claim recap (from public/index.html)

“Many Claude Code chats coding in parallel, one chat at a time on the test bench. Ensemble enforces it at the filesystem so test runs never collide — and your projects rotate through scheduled Plan → Code → Test loops while you sleep, eat, or work elsewhere.”

The pitch makes three falsifiable claims:

  1. Code in parallel, test in single file — many chats work simultaneously; only one tests at a time
  2. Scheduled rotation — projects take turns through the loop on a schedule
  3. Plan → Code → Test loops — Claude runs the full loop, including failure recovery

Today’s reality:

  1. Lock contention applies to ALL autopilot sessions, not just tests. There’s no intent distinction, so coding and testing share the same lock semantics.
  2. No rotation scheduler exists. We have 4 fixed-time daily routines (morning-briefing, evening-planning, overnight-heavy, workday-pulse) that fire against the top_rec project — never multiple, never round-robin.
  3. No loop template. Autopilot fires a single bounded session; the chat decides what to do within it. There’s no canonical prompt that orchestrates plan→code→test→fix→retest.

The 5 mission-critical gaps

Gap 1 — Lock-type semantics ✅ SHIPPED 17b6655 · 2026-04-25

Claim: “Code in parallel. Test in single file.”

Reality: Lock is acquired for all autopilot sessions regardless of what they do.

Proposed design: - Extend state.lock.d/holder.json schema: json { "chat": "boo-website", "intent": "test", "intent_reason": "running xcodebuild test on simulator", "pid": 12345, "acquired_at": "2026-04-25T08:00:00Z" } - intent enum: "test" | "code" | "any" (default "any" for back-compat) - orchestrator_lock.sh (PreToolUse hook) gates only when: - holder.intent == “test” AND incoming tool is test-related (xcrun, xcodebuild, simulator, port-binding, etc.) - OR holder.intent == “any” (legacy) - code intent locks DO NOT block other code intent sessions — they coexist. Only test intent locks contend with each other. - Autopilot session prompts declare intent at acquisition time.

Files affected: - plugins/ensemble/bin/orchestrator_lock.sh — read holder.intent, branch logic - plugins/ensemble/bin/orchestrator_lock_healthcheck.sh — surface intent in banner - bin/autopilot_session.sh — declare intent when acquiring lock - plugins/ensemble/templates/AGENT.md §5 (Autopilot lock) — document new semantics - plugins/ensemble/templates/MAESTRO.md Directive 1 — document new semantics - bin/maestro-context.sh — show holder.intent in lock-held line - bin/morning-digest.sh — same

Success criteria: - Two chats running intent: code autopilot sessions simultaneously: both proceed, no contention. - Two chats both attempting intent: test: second waits or aborts cleanly. - Existing autopilot calls (no intent specified) default to "any" — no breaking change. - Lock holder JSON validates against expanded schema.

Effort: M (~1 hour). Touches the safety-critical lock; needs careful smoke-testing.

Gap 2 — Rotation scheduler ✅ SHIPPED 13bd4ac · 2026-04-25

Claim: “Your projects rotate through scheduled Plan → Code → Test loops.”

Reality: No rotation logic. Routines fire at fixed times against whichever Agent has the highest top_rec.

Proposed design: - New scheduled task: orchestrator-rotation firing every 90–120 min during overnight (e.g. 23:00 / 00:30 / 02:00 / 03:30 / 05:00 — 5 fires). - Each fire: 1. Run prelude. If skip → exit. 2. Read all chats/*.json where active: true AND autopilot_eligible: true. 3. Sort by last_autopilot_fire_at ascending (least-recently-fired first). 4. Pick the first project that doesn’t currently hold the lock. 5. Fire a bounded autopilot session at that project (intent: test, budget 30–45 min). 6. Update last_autopilot_fire_at in the chat’s status file on completion. - Round-robin emerges naturally from “least-recently-fired wins” tiebreak. - Skips inactive projects, Virtuosos (no repo), and the project currently holding the lock.

Files affected: - New: plugins/ensemble/bin/rotation_pick.sh — outputs the next slug to fire - New: ~/.claude/scheduled-tasks/orchestrator-rotation/SKILL.md — the routine - chats/*.json — add last_autopilot_fire_at field (or compute from runs/) - bin/autopilot_session.sh — write last_autopilot_fire_at on completion - docs/AUTOPILOT_DESIGN.md — document rotation semantics

Success criteria: - Over a 5-fire overnight window, 4 of 5 active autopilot-eligible projects each get exactly one autopilot session (round-robin). - If only 2 projects are eligible, they alternate. - A project currently holding the lock is skipped without error; rotation moves to the next candidate.

Effort: M (~90 min). Pure scheduling logic + state tracking.

Depends on: Gap 1 (lock-type semantics) — without that, rotation can’t safely fire test sessions back-to-back.

Gap 3 — Plan → Code → Test → Fix loop template ✅ SHIPPED ab39236 · 2026-04-25

Claim: “Claude takes over automation controls and testing himself, then goes in to fix.”

Reality: Each autopilot session is bounded, but its prompt just says “do the top_rec.” No structured loop.

Proposed design: - New autopilot prompt template at plugins/ensemble/templates/autopilot_loop.txt: Acquire test-intent lock. You have N minutes. Phase 1 (Plan, ~5 min): Read state files, charter, top_rec. Write a precise unit-of-work plan. Phase 2 (Code, ~N/3 min): Implement. Commit at logical checkpoints. Phase 3 (Test, ~N/3 min): Run the test suite or smoke test. Capture results. Phase 4 (Fix loop, remaining time): If tests fail, diagnose + fix + re-test. Maximum 3 attempts within budget. Phase 5 (Wrap, last 2 min): Commit final state. Update SESSION_LOG. Release lock. - bin/autopilot_session.sh reads this template and embeds it in the claude-p prompt for intent: test sessions. - Per-project overrides allowed via chats/<slug>.json::autopilot_loop_override (optional).

Files affected: - New: plugins/ensemble/templates/autopilot_loop.txt - bin/autopilot_session.sh — load + interpolate template - chats/<slug>.json — optional autopilot_loop_override field

Success criteria: - An autopilot session run against a project with failing tests visibly cycles through plan → code → test → fix → re-test in its run log. - Session respects budget; doesn’t enter infinite loops. - If tests pass on first try, phases 4 is skipped; remaining time goes to either next-unit-of-work or graceful wrap.

Effort: S (~30 min). Prompt + small wrapper change.

Depends on: Gap 1 (intent-aware lock) so the test phase actually contends correctly.

Gap 4 — Per-project time-window prefs ✅ SHIPPED b773b26 · 2026-04-25

Claim: Implicit — projects have natural cadences (you wouldn’t fire iOS tests during work hours, but doc work overnight is fine).

Reality: Routines fire blindly across all eligible projects.

Proposed design: - chats/<slug>.json carries: json "preferred_windows": ["overnight", "evening"], "blocked_windows": ["work-hours"] - Window definitions in ~/.claude/orchestrator/work_hours.json (already exists for work-hours; extend for “overnight”, “evening”, etc.). - Rotation scheduler honors prefs: skips projects whose preferred windows don’t include “now.”

Files affected: - chats/*.json — new fields - work_hours.json — define window labels - bin/rotation_pick.sh — filter by current window - AGENT.md §16 / MAESTRO.md Directive 14 — document prefs

Success criteria: - A project with preferred_windows: ["overnight"] is never fired during work-hours rotation. - A project with blocked_windows: ["work-hours"] is skipped at 14:00 even if it’s “next” in round-robin.

Effort: S (~30 min).

Depends on: Gap 2 (rotation scheduler).

Gap 5 — Cross-machine lock awareness 🌐 DEFERRED TO PHASE 2

Claim: Implicit — Spectra Nova lives on Windows; Mac runs Boo, Pinball, Vera Nota. Two machines could collide if both have an Ensemble installation and both want to test.

Reality: Lock state is per-machine. No cloud-sync.

Proposed design (future): - Cloud-synced lock state via private gist or S3. - Each machine writes its state.json.lock_acquired_at + holder info to the shared store. - Acquiring locally also writes to cloud; releasing clears. - Cross-machine conflicts surface in maestro-context briefings.

Files affected (when shipped): - New: bin/lock_sync.sh — push/pull lock state - orchestrator_lock.sh — call sync after acquire/release - state.json — add cloud_sync_enabled flag

Effort: L (~3-4 hours).

Depends on: Stable single-machine implementation of Gaps 1–3 first. Not in this immediate roadmap.

Sequencing — recommended order

Gap 1 (lock-type semantics)      ─┬─→  Gap 2 (rotation scheduler)  ─→  Gap 4 (window prefs)
                                  └─→  Gap 3 (loop template)
                                                                       ↓
                                                                  Gap 5 (cross-machine, future)

Session 1 (next): Gap 1 alone. Foundational + safety-critical; needs careful testing. Ship + smoke-test.

Session 2: Gap 2 + Gap 3 in parallel (rotation needs intent-aware lock; loop template uses intent declaration). Both depend on Gap 1.

Session 3: Gap 4 (window prefs) layered onto rotation.

Phase 2: Gap 5 (cross-machine).

Risk register

  • Lock-type semantics breaking existing autopilot calls — mitigated by "any" default for back-compat. Smoke-test all 4 currently-eligible projects (ensemble, boo-website, pinball-roguelight, vera-nota) before shipping.
  • Rotation firing during user activity — mitigated by mode gate (already implemented) + work-hours prelude (already implemented).
  • Loop template inducing infinite retry — bounded by the Phase 4 max-3-attempts cap + the existing gtimeout wrapper.
  • CI billing wall blocking commits — Kevin’s action; not blocking development since auto-trigger is disabled.

Acceptance — when is the pitch true?

After Sessions 1–3 land:

  • [ ] Lock holder JSON includes intent field
  • [ ] Two chats with intent: code run simultaneously without contention (verified)
  • [ ] Two chats with intent: test contend correctly (one waits) (verified)
  • [ ] orchestrator-rotation scheduled task fires every ~90 min overnight
  • [ ] Rotation distributes fires across ≥3 active projects in a single overnight window
  • [ ] Autopilot session prompts use the autopilot_loop.txt template by default
  • [ ] A test-failure scenario shows visible plan→code→test→fix→re-test cycling in run logs
  • [ ] Per-project preferred_windows honored by rotation
  • [ ] public/index.html pitch claims align with shipped behavior — no asterisks, no “aspirational”

When all 8 boxes are checked, the pitch is true. Until then, the pitch overpromises.
