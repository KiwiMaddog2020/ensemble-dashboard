OPUS_OPTIMIZATION.md — Claude Opus 4.7 Techniques for The Ensemble

Status: synthesis of Anthropic canonical guidance applied to our specific multi-chat orchestration application. 2026-04-23. Sources: Anthropic’s Building effective agents, What’s new in Claude Opus 4.7, Adaptive thinking, Effort parameter, Tool use, Claude Code sub-agents, plus Anthropic’s official Opus 4.7 with Claude Code best-practices post. Audience: every Maestro, Virtuoso, and Agent in The Ensemble. Read once; honor perpetually. Motto: Proper Prior Planning Prevents Piss Poor Performance — the model rewards operators who plan.

0. Why this document exists

The Ensemble runs many Claude Code chats in parallel, each with its own role, each carrying persistent state across weeks. Getting Claude Opus 4.7 to operate at sustained excellence across that topology is an engineering problem, not a vibes problem. This doc codifies what Anthropic’s own best-practice guidance says, applied to our specific stack.

The single most important thing to internalize: Opus 4.7 is more literal and less generalizing than 4.6. The model will no longer silently fill in gaps. Vague prompts now produce scoped-to-the-literal-ask outputs. This is a feature for plan-heavy work and a bug for casual prompting — we must adjust our prompting accordingly.

1. Model + thinking posture per tier

Tier Model Thinking Effort Why
Maestro Opus 4.7 Adaptive, auto high default; xhigh for ranking across portfolios or synthesizing across many status files Maestro makes cross-project decisions; always needs deep reasoning
Virtuoso (Agent Builder, Tool Builder) Opus 4.7 Adaptive, auto xhigh the recommended starting point per Anthropic; max only when evals show headroom Long-horizon planning + research; token budget is not the constraint
Agent (standard worker, one project) Opus 4.7 by default; Sonnet 4.6 acceptable for cost-sensitive mechanical work; never Haiku for Agent-class work except narrow Explore-class lookups Adaptive, auto high for normal coding; xhigh for deep refactors, debugging, multi-file changes Ships code, holds autopilot lock; quality bar is production-shipping
Sub-agents (Explore, Plan, general-purpose — invoked by Claude Code) Claude Code picks — Explore uses Haiku, others inherit Inherited Inherited We don’t override; Claude Code’s routing is sound

Key Opus 4.7 facts: - thinking: {type: "enabled", budget_tokens: N} is rejected with a 400 error on 4.7. Adaptive is the only supported thinking mode. - On 4.7, thinking is off unless thinking: {type: "adaptive"} is set. Claude Code handles this automatically; when we write our own API callers (e.g. for Tool Builder’s router SDK), we must set it explicitly. - Thinking display defaults to omitted on 4.7 (silent change from 4.6). Set display: "summarized" if a downstream consumer needs to read thinking. - temperature, top_p, top_k are rejected — prompt to guide behavior. - New tokenizer uses ~1.0–1.35× as many tokens as 4.6. Budget headroom; update max_tokens defaults.

2. The 4.7 behavior shift — explicit > implicit

Quotes from Anthropic’s 4.7 launch notes, verbatim:

“4.6 silently filled in implicit context while 4.7 does not, so you should rewrite prompts with explicit intent, success criteria, and constraints.”

“4.7 rewards operators who invest in planning… every hour spent on a detailed plan output pays back across the execution phase.”

“More literal instruction following, particularly at lower effort levels. The model will not silently generalize an instruction from one item to another, and will not infer requests you didn’t make.”

What this means for Ensemble prompts:

  • Every AskUserQuestion option description must state explicit scope — “produce 3 files: A, B, C” not “produce the deliverables.”
  • Every Virtuoso/Agent charter must state explicit success criteria per phase gate (our handoff docs already do this).
  • Every autopilot pre-flight must list exact files to be touched, exact commit message format, exact commit count. No “and similar.”
  • Avoid “and related cleanup” / “adjacent polish” in instructions — they become no-ops on 4.7.

Prompting pattern that works on 4.7:

GOAL: <one-sentence outcome>
SCOPE:
- Touch exactly these files: [list]
- Do not touch: [list of off-limits]
DELIVERABLE: <specific artifact, e.g. "one commit on plugin-refactor, not pushed">
SUCCESS CRITERIA:
- [ ] criterion 1 (verifiable)
- [ ] criterion 2 (verifiable)
STOP CONDITION: <when to halt and report>

This is what Anthropic calls “explicit task briefs,” and it’s what 4.7 rewards.

3. Effort + adaptive thinking — what we control in Claude Code vs the API

In Claude Code (the environment every Ensemble chat runs in): - Effort level is managed by Claude Code’s session configuration — we don’t set it per-turn. - Adaptive thinking is on by default on 4.7. - We CAN influence thinking depth via prompting. Anthropic’s guidance: - More thinking: “Think carefully and step-by-step before responding.” - Less thinking: “Prioritize responding quickly rather than thinking deeply.” - We CAN influence tool-call density via prompting — Anthropic says 4.7 defaults to fewer tool calls and uses reasoning more. If parallel tool fan-out is genuinely useful, say so explicitly (“call these four WebFetches in parallel”).

In our own Opus-calling code (Tool Builder’s router, Agent Builder’s fine-tune pipeline, etc. — not yet built but coming): - Set thinking: {type: "adaptive"} explicitly. - Set output_config.effort per task type: xhigh for agentic/coding, high for reasoning, medium for classification/extraction/formatting, low only for trivial lookups. - For long-running tasks, investigate task_budget (beta header task-budgets-2026-03-13) — gives the model a soft token allowance and a running countdown so it self-moderates. - Never set temperature, top_p, or top_k — 400 error on 4.7.

4. Prompting discipline — the five levers that matter most

4.1 Explicit intent + success criteria

Covered in §2. Non-negotiable on 4.7.

4.2 XML tagging for structured inputs

When a prompt carries multiple distinct chunks of context (repo state + charter + user question + prior status), wrap each in XML tags:

<repo_state>
<!-- git status output -->
</repo_state>
<charter>
<!-- PROJECT_CHARTER.md content -->
</charter>
<user_question>
<!-- the actual ask -->
</user_question>

Claude is trained on this pattern. It parses tagged inputs more reliably than unstructured blobs and responds with cleaner delineation between reasoning and output.

4.3 Role prompting via durable identity files

Our AGENT.md and MAESTRO.md and the per-Virtuoso handoff docs ARE role prompts. They persist across turns. This is a strength of the Ensemble architecture that many frameworks lack.

4.4 Prefilling for format control

When we need a strict output format (JSON, a specific markdown structure, a commit-message template), prefill the assistant’s response opening. Claude Code’s Edit tool is effectively this pattern for file content; for chat responses, start the response with the format skeleton:

Starting assistant message:
TOP REC: <headline>
  Why:

This forces Claude to continue the structure rather than reinvent.

4.5 Multishot / few-shot examples

For tasks with ambiguous format or judgment boundaries, include 2–3 examples in the prompt. Especially valuable for: - Classification tasks (data-class tagging for the cognition router) - Commit message format - Rapid-fire report shape - LLM_SPEC.md schema adherence

Our templates already contain examples where they matter (commit message format in charter, rapid-fire block in AGENT.md §2). Extend this discipline when building new templates.

5. Tool use — parallel calls, error recovery, strict schemas

5.1 Parallel tool fan-out

When independent calls can run concurrently, issue them in a single tool-use block. Examples from today’s work: - Fetching 6 Anthropic docs in parallel (3x faster than sequential). - Batching parallel Reads before a multi-file Edit sweep. - Running Grep + Glob + Bash version-check in one burst during exploration.

4.7 tends toward fewer tool calls by default. Explicitly request parallelism when it’s the right shape.

5.2 Tool descriptions — invest as much effort as in human-computer interfaces

Anthropic’s canonical advice: “Invest effort equal to human-computer interface design.”

For our custom tools (the router SDK we’ll build for Tool Builder / Agent Builder): - Use absolute paths, not relative (compounding errors). - Provide explicit context tokens before demanding output (examples, edge cases). - Match internet-trained patterns (standard HTTP verbs, standard JSON shapes, not custom DSLs). - Include example usage in the tool description. Include what bad input looks like. - Apply poka-yoke — make wrong calls impossible via schema, not via docs.

5.3 Strict tool use

For our own tools, set strict: true. Guarantees schema conformance. Prevents drift where the model guesses a field name.

5.4 Error recovery

When a tool errors: - Do not retry in a loop without diagnosing. - The error message itself is often the guidance — read it. - If the error is truly intermittent, one retry with explicit backoff is OK; three retries means you’re fighting a real issue.

5.5 Agentic-loop durability

For long tool-use loops (autopilot windows, router dispatches that chain K→L→O→C tiers): - Log every tool call + result to persistent state so a mid-loop failure can resume. - Define a hard budget (time or tokens) and terminate gracefully when exceeded. - Produce a review-queue artifact, never a silent commit.

6. Sub-agents (within a chat)

Claude Code provides three built-in sub-agents: Explore (Haiku-backed, read-only, for codebase search), Plan (inherits model, read-only, for plan-mode research), general-purpose (inherits model, all tools, for complex multi-step). Plus user-defined sub-agents via /agents.

When to delegate: - A side task would flood the main conversation with file contents, logs, or search output we won’t re-reference. - A task matches a repeatable pattern (write a custom sub-agent once, reuse). - We want to enforce tool restrictions (e.g. a “security-reviewer” sub-agent with read-only access). - We want context isolation so the parent conversation stays lean.

When NOT to delegate: - The task is the main conversation’s core concern — delegating hides reasoning. - The task is trivial — overhead of spawn + brief exceeds the saved context. - The task needs to mutate state (write files, commits) and we haven’t granted the sub-agent permission.

Brief discipline for sub-agent prompts: Anthropic’s explicit guidance applies extra here — sub-agents start cold, no conversation history. Every prompt must stand alone with: goal, constraints, what’s been tried, exact format expected in return. Short reports demand: “report in under 200 words.”

Opus 4.7 spawns fewer sub-agents by default than 4.6. If parallel sub-agent fan-out helps — say Track A legal research on multiple compliance regimes in parallel — explicitly request it.

7. Agent teams (across chats) — The Ensemble, properly used

Anthropic’s own distinction: “Subagents work within a single session; agent teams coordinate across separate sessions.” That’s the Ensemble. Our Maestro + multiple Agents + two Virtuosos = a canonical agent team.

7.1 Canonical patterns applied

Anthropic pattern Ensemble application
Prompt chaining Agent Builder’s 9-track research → LLM_SPEC.md → fine-tune → deploy. Sequential, state-file-mediated.
Routing Maestro’s cross-project top-rec dispatch. Also the cognition router (K/L/O/C) inside deployed LLMs.
Parallelization — sectioning 9 research tracks in parallel. Three Virtuosi / Agents operating on different projects simultaneously (constrained only by the autopilot lock).
Parallelization — voting Not yet used; candidate for hard eval cases where we want diverse outputs on the same prompt.
Orchestrator-workers Literally The Ensemble — Maestro orchestrates, Agents are workers, Virtuosi are elevated workers.

7.2 The load-bearing primitives of our agent-team architecture

  1. The shared state file (${CLAUDE_PLUGIN_DATA}/state.json) — atomic reads/writes, single source of truth.
  2. The atomic autopilot lock (POSIX mkdir) — one winner, no races.
  3. Per-chat status files (chats/<slug>.json) — heartbeats, top recs, roster visibility.
  4. Per-repo charters (.claude/PROJECT_CHARTER.md) — durable truth that survives context compaction.
  5. Hooks (PreToolUse + SessionStart) — enforce safety outside the conversation.
  6. Signal phrases (***ORCHESTRATOR OFF*** + five others) — verbatim triggers that any chat recognizes.
  7. The six-phase kill-switch cascade — distributed, idempotent, works under race.

These are our infrastructure. They’re what lets us run Opus 4.7 across 5+ chats safely.

8. Persistent state — Opus 4.7’s memory improvements

Anthropic’s 4.7 release notes, verbatim:

“Claude Opus 4.7 is better at writing and using file-system-based memory. If an agent maintains a scratchpad, notes file, or structured memory store across turns, that agent should improve at jotting down notes to itself and leveraging its notes in future tasks.”

Our chats/*.json + .claude/PROJECT_CHARTER.md + append-only decision logs in per-Virtuoso identity files ARE this pattern. 4.7 strengthens our bet here.

Good practices: - Every meaningful decision writes to a durable log with a timestamp. - Every status file heartbeat captures enough context to reconstruct the chat’s intent cold. - Charter updates append-only where possible — preserve history. - When a chat’s context is about to compact, summarize to the status file first.

The Tool Builder Virtuoso’s self-spawned chats/tool-builder.json is a gold-standard example — 200 lines of scannable state, every research track tracked, every phase gate enumerated, every safety rail listed.

9. Context budget management

Opus 4.7 has a 1M token context window. That is ample — but not infinite, and not free.

Compaction avoidance tactics: - Parallel sub-agent delegation for “find and summarize” tasks (keeps raw file contents out of parent context). - Explicit state-file writes at end of any research phase (can be re-read cheaply; doesn’t need to stay in-context). - Prune tool output: request “under 200 words” from sub-agents when raw data is what we don’t need. - Use Explore sub-agent for read-only codebase search (Haiku-backed, cheap, returns summaries).

Rehydration after compaction: - Every chat’s first action on session start: read its charter, its status file, its identity file. The state IS the memory. - Don’t rely on in-context conversation history for durable knowledge — that’s fragile.

10. Anti-patterns (things we refuse to do)

  1. Asking Claude to “also do related cleanup.” 4.7 either does exactly that, or nothing. Be specific.
  2. Assuming 4.7 will infer unstated constraints. It won’t.
  3. Leaving temperature or top_p set in our own code. Will 400-error on 4.7.
  4. Setting thinking.budget_tokens. Deprecated on 4.6, rejected on 4.7. Use adaptive + effort.
  5. Running max effort on structured-output tasks. Anthropic warns: “On some structured-output or less intelligence-sensitive tasks it can lead to overthinking.” Stay at high or xhigh.
  6. Spawning sub-agents for trivial tasks. Overhead > benefit.
  7. Forgetting to mark the recommended option with (Recommended) in the LABEL of an AskUserQuestion. Per AGENT.md §2 / MAESTRO.md §2 directive 7.
  8. Retrying a failing tool call without reading the error. The error is the guidance.
  9. Destructive git ops without per-turn approval — --force, reset --hard after push, history rewrite, branch/tag deletion. Per safety_constraints.md. (git push on current branch is NOT gated as of 2026-04-24.)
  10. Relying on in-context history as durable state. Write it to the status file or charter.

11. Checklist for every chat’s first turn

Regardless of tier, every Ensemble chat on session start:

  1. Read state.json (or ask user for direct-mode if missing).
  2. Read the relevant contract (MAESTRO.md for Maestro, AGENT.md for Agents, the specific handoff doc for Virtuosos).
  3. Read the per-repo PROJECT_CHARTER.md (if Agent-tier scoped to a repo).
  4. Read or write the own status file at chats/<slug>.json with fresh last_heartbeat.
  5. Scan any new deliverables in the repo since the last heartbeat.
  6. Report in rapid-fire: TOP REC + 2–3 alternatives via AskUserQuestion with (Recommended) on the first option’s label.
  7. Wait.

This is the Opus 4.7 “invest in a plan output” principle encoded as a protocol.

12. Continuous improvement

  • Every engagement (or every sprint for internal work) ends with a micro-retrospective written to the decision log — what prompting shape worked, what didn’t, what took longer than estimated.
  • Track “prompt rewrites required” as a quality metric: if we had to re-prompt 3× to get a specific output, the original prompt was under-specified; the retrospective captures what the right prompt shape is.
  • Feed learnings back into the contract templates (MAESTRO.md, AGENT.md) via commits to plugins/ensemble/templates/. This is how the Ensemble gets sharper over time.
  • When a technique is adopted permanently, reference this doc from the relevant charter section so future chats inherit.

13. Summary — the seven rules that matter most

  1. Explicit > implicit. 4.7 doesn’t fill in gaps. State scope, success criteria, stop condition.
  2. xhigh effort is the default for coding + agentic work. Don’t stay at high out of habit.
  3. Adaptive thinking only on 4.7. No budget_tokens.
  4. Parallel tool calls when independent. 4.7 defaults to fewer; ask for the fan-out.
  5. Write state to durable files, not in-context memory. Charters, status files, decision logs.
  6. (Recommended) belongs in the LABEL of AskUserQuestion, never the description.
  7. Batched approvals at the logical-unit level. Per AGENT.md §2 and MAESTRO.md §2 directive 12.

If every chat in The Ensemble internalizes those seven rules, the coordination across many Opus 4.7 instances is tight. If even one chat drifts on them, we start losing the quality-per-token ratio that makes the Ensemble worth running.
