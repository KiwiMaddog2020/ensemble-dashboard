GRAND_PLAN.md — The Ensemble → Agent Builder → Tool Builder (three products, one integrated suite)

Status: strategic plan, 2026-04-22 (revised same-day with Kevin’s cognition-flexibility + amalgamation corrections). Author: Kevin (vision) + Maestro (synthesis + tech-stack research). Audience: future-Kevin, future-Agents spawned for Phase 2+ projects, future-contributors if the plan goes public. Scope: no implementation in this doc. This is direction + architecture + known-unknowns. Individual Phases get their own design docs (e.g. virtuosos/agent-builder/DESIGN.md) when we’re ready to build them. Motto: Proper Prior Planning Prevents Piss Poor Performance.

Founding principles (read these before anything else)

These override anything that contradicts them later in the doc.

  1. Rocket-grade engineering. This is not web-app engineering. We’re building a system that will eventually run inside regulated industries, on client hardware, in critical workflows. Every design decision gets shuttle-launch scrutiny — pre-mortems, explicit failure modes, redundancy, the 6 P’s. Fast is a byproduct of ruthlessly eliminating rework; it is never the goal.
  2. Apple-grade user experience. The setup feels like unboxing an Apple product: dense capability, invisible complexity, delight in the small moments. “Considering the scope” is an internal concern, never a user-facing excuse. The shiny package is part of the engineering.
  3. Cognition flexibility is a feature, not a concession. Every chatbot and every AI surface we build must support Claude integration as an option. But the primary runtime is the client’s choice: a custom fine-tuned LLM, an open-weight model on their hardware, a commercial API (Claude, Gemini, etc.), or a hybrid that routes by task. We never lock a client into one vendor. See §3.1.
  4. Private by default, powerful by choice. Privacy is the ground state. Clients who want full-cloud can opt in; clients who want air-gapped get it. The architecture supports both without forks.
  5. Three products, one integrated suite. Ensemble, Agent Builder, and Tool Builder (Phase 0/1/2 — see §1) amalgamate. They are not three standalone offerings that share a logo. A client using Tool Builder gets tools that embed an Agent Builder-crafted LLM and are built by an Ensemble of Agents. The packaging to the client is one thing: “your AI-native business, shipped.”
  6. Human-approval gate on destructive + publishing external state. Per safety_constraints.md (updated 2026-04-24). Destructive git ops, App Store / Play Store / TestFlight submissions, deploys beyond GitHub Pages auto-deploy, public-flip of private repos, and billing changes all require explicit per-turn approval. git push to origin on the current branch is NOT gated — commit + push flows freely. Recursive loops may push proposed changes; humans review + intervene if needed.

0. What this document is

Kevin has an arc: The Ensemble is Phase 0 of a larger vision that culminates in a packaged AI-integration product for small and mid-market businesses. This doc captures:

  1. The full product ladder — each rung building on the one below.
  2. The unifying architectural pattern that makes it all one thing, not three unrelated products.
  3. Tech-stack decisions — what to leverage (existing OSS), what to build (our differentiator), what to defer (not yet worth the added surface area).
  4. Privacy tiers — how the same architecture serves a regulated healthcare client and a scrappy 10-person SMB without collapsing.
  5. A phased roadmap with explicit critical path and off-ramps.
  6. Risks, unknowns, and the specific decisions that need to happen before each phase begins.

It does not commit Kevin to anything. It’s a shuttle-launch checklist: an item is either ready, not ready, or not even the right item to check for right now.

1. The product ladder

Phase Product Internal tier Customer Primary value
0 — now The Ensemble The system itself — Maestro + Agents Solo developer (Kevin) Multi-chat Claude Code orchestration. Builds software at shuttle-launch standard.
1 — next Agent Builder Virtuoso-tier (elevated special-purpose builder) Non-technical individual, small team, or SMB buying a custom agent Interview-driven pipeline that produces a client-specific LLM (or hybrid LLM + KB + orchestration) tailored to one use case. Privacy-tier-aware.
2 Tool Builder Virtuoso-tier (elevated special-purpose builder) SMB owner / ops lead Scan the business + competition, design AI-integrated in-house tools (websites, PWAs, native apps, CRM, team chat, inventory, dashboards), build + deploy them — each tool hosts an Agent Builder LLM inside it.

Phase 0 is live. Phase 1 has been sketched but never built (the old “LLM Creation Toolkit” project never scaffolded). Phase 2 and 3 are new explicit scope from 2026-04-22.

1.1. How the three products amalgamate (the critical architectural claim)

These are not three products that happen to share a codebase. They are one stack with three surfaces:

                  ┌────────────────────────────────────────────────────┐
                  │  Unified Suite (Phase 3 — the shipping carton)      │
                  │                                                    │
                  │   ┌─────────────────────────────────────────────┐  │
                  │   │  Tool Builder tools (Phase 2)                    │  │
                  │   │  CRM · chat · inventory · website · ...     │  │
                  │   │                                             │  │
                  │   │   ┌─────────────────────────────────────┐   │  │
                  │   │   │  Agent Builder LLM (Phase 1)              │   │  │
                  │   │   │  fine-tuned on client's KB,         │   │  │
                  │   │   │  runs on client's privacy tier      │   │  │
                  │   │   └─────────────────────────────────────┘   │  │
                  │   │                                             │  │
                  │   │   …embedded inside the tool as its AI layer │  │
                  │   └─────────────────────────────────────────────┘  │
                  │                                                    │
                  │  All three built + maintained by the Ensemble      │
                  │  (Phase 0 orchestrator + Agents).                │
                  └────────────────────────────────────────────────────┘

Concrete example of what amalgamation means in practice:

A boutique retail client signs up for the Unified Suite. We run Tool Builder’s scan, we pick three tools (a customer-service chat widget, an inventory dashboard, a marketing-copy generator). We run Agent Builder once per tool to fine-tune a Qwen 2.5 14B on: - their product catalog (for the chat widget), - their sales history (for the inventory dashboard), - their brand voice corpus (for the marketing-copy tool).

Each tool embeds its own Agent Builder-crafted LLM. The client’s data never leaves their infra (Tier 2). The Ensemble built + deployed + maintains all of it.

The client sees one product: “our AI-native business.” They never see the three-phase architecture unless they ask.

1.2. Naming — the three-tier taxonomy

Kevin’s 2026-04-22 direction: keep Ensemble as the umbrella brand, keep Maestro as the controller, rename the rank-and-file to Agents, and reserve Virtuoso as a tier designation for the two elevated special-purpose builders — Agent Builder and Tool Builder.

The three tiers:

Tier Role Count Examples
Maestro Controller chat. Orchestrates the portfolio, ranks top recs, never holds the autopilot lock. 1 per system This chat.
Virtuoso Elevated special-purpose builder. Runs a multi-week planning + interview + construction process whose output (an LLM, a tool suite) is what a client uses. Bigger scope, longer horizon, stricter Apple-grade bar. Two products to start (Agent Builder, Tool Builder); more can be added later. Agent Builder, Tool Builder.
Agent Standard worker chat scoped to one project (a repo, a module, a deliverable). Ships code. Acquires the autopilot lock. Reports in rapid-fire. Many; one per project. BOO-Website, Vera Nota, Pinball Roguelight; build-time Agents spawned by a Virtuoso during construction.

Why Virtuoso fits the elevated tier: a virtuoso is a master performer — someone who has mastered one instrument (or one craft) and operates at a level most performers don’t reach. Agent Builder masters the craft of shaping custom LLMs; Tool Builder masters the craft of designing AI-native business software. “Agent” fits the general worker; “Virtuoso” fits the mastery class. The two-word product names (Agent Builder, Tool Builder) are also SMB-legible for the eventual client-facing materials.

Why these names over alternatives: earlier drafts tried musical metaphors (Luthier, Atelier) that were precise but obscure. Then generic industrial frames (Agency, Controller, Agent). Kevin settled on hybrid: Ensemble + Maestro stay (they’re shipped and they work); Virtuoso stays but gets promoted from “regular chat” to “elevated tier”; Agent replaces the general-worker sense of Virtuoso. The result is three tiers, two of which survive from the original musical family, plus the literal “Agent” for the rank-and-file.

The strategic bet: the same orchestration pattern works at every rung. Each rung is the previous rung with a different intake surface and a different output surface. We don’t re-invent the machinery — we re-skin it. And because the output of each phase is the input of the next, they compose into a single suite rather than stacking as separate SKUs.

2. The unifying pattern (this is the key insight)

Every rung of the ladder is the same six-step loop:

┌─────────┐  ┌───────┐  ┌──────┐  ┌───────┐  ┌──────┐  ┌──────┐
│ Intake  ├─►│ Scan  ├─►│ Plan ├─►│ Build ├─►│ Ship ├─►│ Loop │
└─────────┘  └───────┘  └──────┘  └───────┘  └──────┘  └──┬───┘
                                                          │
                                            ◄─────────────┘

What changes per rung is the I/O, not the engine:

Step Phase 0 (Ensemble) Phase 1 (Agent Builder) Phase 2 (Tool Builder)
Intake Repo + bootstrap prompt Conversational interview about use case + privacy tier + cognition preference (Claude / local / hybrid) Conversational interview about the business + competitive landscape
Scan Detect stack, read repo Inventory client’s knowledge sources, baseline eval on current workflow Scrape competitor sites, audit client stack, map social + review surface
Plan PROJECT_CHARTER.md LLM_SPEC.md (intended behavior, safety, eval set, deployment target, cognition routing rules) BUSINESS_ROADMAP.md (prioritized tool list + ROI estimate + which Agent Builder LLMs each tool will embed)
Build Agents write code Fine-tune / compose / RAG / agent-chain → Agent Builder LLM artifact Agents build CRM / chat / inventory / website / dashboards — each embeds one or more Agent Builder LLMs as its AI layer
Ship Commit, PR, deploy Deploy model to client infra at chosen privacy tier; publish eval report Deploy apps to client infra; wire in Agent Builder LLMs; hand over admin + runbook
Loop Morning briefing, overnight autopilot Ongoing eval + re-fine-tune on new client data Ops-tier Ensemble watches usage across tools, proposes updates, routes back through Agent Builder for model refreshes

Why this matters: we write Phase 1 and Phase 2 as configurations of the Ensemble machinery, not as separate products. The Ensemble plugin already knows how to spawn specialized Agents, coordinate them, enforce safety, accept phone dispatch. Agent Builder = Ensemble with a different onboarding skill + different Agent templates + LLM_SPEC.md as output. Tool Builder = Ensemble with a different onboarding skill + business-scan Agents + BUSINESS_ROADMAP.md → a portfolio of tool repos, each with an Agent Builder LLM embedded.

And because Tool Builder consumes Agent Builder output, and Ensemble builds both, the three products compose at runtime. A client doesn’t buy “Agent Builder + Tool Builder”; they buy the Unified Suite, and the phases are internal architecture.

This is the architectural discipline that keeps the surface area flat as the product ladder grows.

3. Tech stack — leverage vs build vs defer

Leverage policy: prefer a small number of mature, well-maintained OSS deps over writing our own. Every accepted dep must pass three gates:

  1. Net simplicity — does it remove more code than it adds? (A library with its own DSL usually fails this.)
  2. Stay-in-lane — does it handle one thing well, or is it a kitchen sink? (Avoid LangChain-as-Framework; consider LangChain-as-utilities.)
  3. Anthropic-compatible — does it assume OpenAI-only or does it let us stay with Claude as the cognition engine?

3.1 Cognition (the “thinking” layer) — flexibility is the design

The cognition architecture is per-phase different because the customer is different. For Ensemble (Phase 0) we make one vendor bet because it’s our internal tool. For Agent Builder + Tool Builder (Phase 1 + 2) the client’s business has different needs than our internal needs, so we build for vendor-pluggability from day one.

3.1.a Phase 0 — The Ensemble (internal, Kevin)

Claude is the primary. No change.

Component Choice
Orchestrator reasoning Claude API (Opus 4.7) — the Ensemble IS a Claude amplifier, by design.
Cheap reasoning Claude Haiku 4.5 — already in use for light routines.
Embeddings OpenAI text-embedding-3-large via API — fast, cheap, works.

3.1.b Phase 1 + 2 — Agent Builder + Tool Builder (client-facing) — hybrid cognition with per-task routing

Every client-facing AI surface routes across four cognition tiers based on the task. The routing is defined at Agent Builder-time in LLM_SPEC.md and can be changed by the client at any time.

Tier What runs there Typical use
K — Knowledge base lookup Pure retrieval (pgvector + BM25 + re-rank). No generation. Factual answers with citations. Cheapest. Must-be-right queries.
L — Local custom LLM (Agent Builder-built) Fine-tuned Qwen / Llama / Mistral / Phi running on client infra via Ollama or vLLM. Domain-specific generation, brand-voice writing, classification, extraction. Private by default.
O — Open-weight LLM (general-purpose) Un-tuned open-weight (Llama 3.1 70B, Qwen 2.5 72B) on client infra or inside client VPC. General reasoning that the custom model can’t handle. No data exits client boundary.
C — Commercial API (opt-in) Claude (Sonnet/Opus), Gemini, GPT-5, etc. — client chooses vendors. Hardest reasoning tasks when the client has opted in to send that class of data over the wire. Configurable per-task + per-data-class.

The default routing policy (clients can override per-task):

request
   │
   ▼
 classify data-class (pii? proprietary? internal? public?)
   │
   ▼
 is the answer in the KB with high confidence?
   ├── yes → serve K (citations) → return
   └── no ↓
   │
   ▼
 is this a task the Agent Builder LLM is trained for?
   ├── yes → serve L → return
   └── no ↓
   │
   ▼
 is data-class allowed to leave client infra?
   ├── no → serve O (local open-weight) → return
   └── yes ↓
   │
   ▼
 serve C (client's chosen commercial provider — Claude by default if opted in)

This means: - Every chatbot supports Claude integration — Tier C slot is always wired, even if it’s currently disabled for that client. - Every chatbot works without Claude — Tiers K + L + O cover the zero-external-cognition path. - Clients can go fully exclusive either direction — “Claude only, no local” or “local only, no cloud.” Same architecture, different policy. - Hybrid is the default for clients who don’t care: use each tier where it’s best.

3.1.c Cognition-stack components

Component Choice Phase
KB tier retrieval pgvector + BM25 + bge-reranker-v2 (free, local) OR Cohere Rerank (paid, better) 1+
Local LLM serving Ollama (default) / vLLM (GPU) / llama.cpp (edge) 1+
Fine-tune engine Unsloth (primary) + HuggingFace TRL (features) 1+
Base-model shortlist Qwen 2.5 14B (default), Llama 3.1 8B / 70B, Mistral Small, Phi-3.5-mini, Gemma 2 9B 1+
Commercial providers (Tier C) Claude (Anthropic) always wired. Secondary: Gemini (Google), OpenAI, Mistral (cloud), Cohere. Selected per-client. 1+
Router Custom — a small Python/TS service that reads the LLM_SPEC.md routing rules and dispatches. Simple enough to own; too central to hand to a framework. 1+
Embeddings — cloud OK OpenAI text-embedding-3-large (best quality/$) 1+
Embeddings — private nomic-embed-text or bge-m3 via Ollama 1+

3.1.d Why we own the router

The router is the most load-bearing piece of client-facing code. It enforces privacy-tier boundaries (§4), it chooses cognition, it logs everything for audit. Third-party routers (e.g. OpenRouter) assume the whole world is cloud APIs; they don’t reason about “send to Tier C only if data-class is public.” We write ours.

Tiny — low hundreds of lines. The reasoning is in the LLM_SPEC.md, not the code.

Library When

Base model shortlist (open-weight, non-restrictive license, Unsloth-supported):

  • Qwen 2.5 14B — strong general + coding. First choice.
  • Llama 3.1 8B / 70B — Meta ecosystem weight. Good fallback.
  • Mistral Small / Medium — Apache license. Use when license politics matters.
  • Phi-3.5-mini — 3.8B parameters, surprisingly capable. For on-device-only clients.
  • Gemma 2 9B — Google weights. Strong for size.

3.8 In-house business tool scaffolds (Phase 2 deliverables)

When we build a CRM, chat, inventory system, website, or dashboard for a client, we don’t start from zero. These are the reference starting points:

Deliverable type Default stack
Custom web app (any) Next.js 15 + Supabase (Postgres + auth + storage + edge functions). Boring, reliable, cheap.
Admin panel / internal tool Refine (React-based) OR Retool self-hosted (paid-but-cheap, huge leverage). Test both on first build.
Team chat Mattermost (self-host) — Slack-equivalent, open-source.
Video / meetings Defer — no good OSS match for client expectations. Recommend Google Meet / Zoom for now.
E-commerce / inventory Medusa (Shopify-equivalent, open-source) OR custom Postgres + Next.js if the client needs unusual workflows.
Docs / wiki Outline (Slack-integrated wiki) OR BookStack.
Form builder / intake Formbricks (self-host, OSS).
Workflow automation n8n (self-host) — fair-code license, huge node catalog. Replaces Zapier for a client who doesn’t want per-task SaaS fees.

3.9 What we DON’T adopt (and why)

  • LangChain as a framework — too much churn, too much abstraction, Claude isn’t first-class. OK as a loader library (import specific utilities); not OK as the orchestrator.
  • Haystack — older, smaller ecosystem than LlamaIndex.
  • Pinecone / Weaviate / Qdrant (as vector DB) — overkill at our scale; lock-in we don’t need. pgvector buys us everything through the first 50 clients.
  • Ray / Dask — distributed compute we don’t need. A single fine-tuning box is enough through Phase 2.
  • Kubernetes as default — operational tax that doesn’t pay off at our client scale. Docker Compose first; graduate to k8s only when a single client needs HA.
  • Helm charts, Terraform modules — same argument. Defer until a client has real infra-as-code requirements.

3.10 What’s genuinely uncertain

  • Vector DB at 100M+ vectors — pgvector might not hold. Plan a re-eval at Phase 3.
  • Reranker quality — BGE models are good enough for us now, but commercial Cohere is meaningfully better. Re-test at Phase 2.
  • On-device inference for privacy-tier-1 clients — llama.cpp quality on M-series is great, but we haven’t validated the client-install UX. Needs a pilot.
  • Fine-tuning budget per client — unclear until we do our first 3 real client builds. Hypothesis: $500–2000 in GPU time for Phase 1; $2k–10k for Phase 2 mid-sized client.

4. Privacy tiers (the framework for serving different client risk profiles)

Tier Deployment Who it’s for Data movement
T1 — On-prem / air-gapped Client’s own hardware; no outbound calls during inference. Healthcare (HIPAA), finance (SOX), legal (privilege), defense. Data never leaves. Fine-tuning done on client premises or on approved cloud with DPA.
T2 — Client VPC AWS / GCP / Azure tenant owned by client. We have admin during build; revoked post-handoff. Mid-market, regulated-adjacent. Data stays in client cloud boundary. Claude API calls go direct (covered by Anthropic BAA where applicable).
T3 — Managed cloud (tenant-isolated) Our infra, one schema per client in shared Postgres, encrypted at rest, RLS. SMB default. Client data stored by us under DPA. We own uptime.
T4 — Shared cloud (multi-tenant) Our infra, row-level isolation. Smallest clients, prosumers. Client data stored by us; cheaper, less isolation.

Data-classification tags on every agent output:

  • pii / phi / pci — never crosses to lower-privacy tiers.
  • proprietary — client-bounded; no training on it without opt-in.
  • internal — inside the client’s org, but not sensitive.
  • public — OK to use in aggregated prompts or (with opt-in) training data.

The orchestrator has a hook that refuses to ship an output to a lower-privacy sink than its tags allow. Same pattern as the autopilot lock: fail closed, surface the attempt, log it.

5. The Agent Builder Interview (Phase 1 intake)

This is the Virtuoso-tier chat Kevin described — the “special” builder whose job is not to ship code but to shape a client’s raw need into a manufacturable LLM spec. Agent Builder is one of two Virtuosos (the other is Tool Builder; see §6). Replaces “drop a repo” with “describe a goal.” Designed for non-technical users. UX target: Apple-product onboarding quality (see Founding Principle §2).

Conversational interview structure (adaptive — skip branches based on answers):

  1. Who are you? — individual / team / business; technical / non-technical; industry.
  2. What outcome do you want? — describe the problem, not the solution. (“I waste 4 hours a week answering the same customer emails.”)
  3. How do you do this today? — existing tools, workflows, pain points.
  4. What data could help? — documents, databases, chat logs, calendars, emails.
  5. Who can see what? — privacy tier, data classes, consent boundaries.
  6. What does “done” look like? — specific, measurable success criteria.
  7. What’s your budget + timeline? — money, calendar time, GPU time.
  8. What’s your risk tolerance? — ship fast vs. ship careful.
  9. Cognition preferences (new — per Kevin’s 2026-04-22 direction) — which of Tiers K / L / O / C (see §3.1.b) are you open to? “Local only,” “Claude integration welcome for hardest tasks,” “fully cloud,” “surprise me with a hybrid.” The answer sets the default routing policy in LLM_SPEC.md; client can flip it any time post-deploy.

Output artifact: LLM_SPEC.md — structured spec containing:

  • Problem statement.
  • Target behaviors (with examples).
  • Non-behaviors (things the LLM must refuse or escalate).
  • Knowledge sources + ingestion plan.
  • Privacy tier + data-class map.
  • Eval set (10–30 labeled examples the LLM must pass).
  • Deployment target (Ollama local, client VPC, etc.).
  • Monitoring + update cadence.

Build flow (after the interview):

  1. Assemble baseline — pick base model, RAG or fine-tune or both.
  2. Produce candidate v0 — quick build, usually in the first 30 min post-interview.
  3. Run eval set — promptfoo against the 10–30 examples.
  4. Iterate — adjust prompt / re-fine-tune / tune retrieval until eval passes.
  5. User acceptance — live session with the user driving, we watch.
  6. Ship — deploy to chosen target, hand over docs + monitoring.
  7. Ongoing loop — monthly re-eval, new examples added, model updated.

Unifying-pattern check: this is the Ensemble’s onboarding + autopilot loop with a different output artifact. ✓

6. Tool Builder — the Business Tool Workshop (Phase 2 intake + build)

Same shape as Agent Builder, scaled up to a business + its competitive environment. This is where the amalgamation becomes visible: every tool Tool Builder ships embeds one or more Agent Builder LLMs as its AI layer. The tools aren’t “AI-bolted-on”; they’re AI-native from the first commit.

Scan pipeline:

  1. Business intake — website URL, basic info, industry, privacy tier preference.
  2. Competitor discovery — Google queries + industry lists; user confirms a shortlist of 3–7 competitors.
  3. Scrape + normalize — Firecrawl each site into markdown; Wappalyzer detects stack; capture marketing copy, pricing, feature list.
  4. Social + review surface — Google Business reviews, LinkedIn presence, Glassdoor (if B2B), Trustpilot (if consumer).
  5. Client stack audit — guided interview: what CRM, what chat, what docs, what inventory, what ops tools. Plus: what do you hate about your current stack?
  6. Gap analysis — Claude ranks opportunities by impact × feasibility, produces a build list. Each candidate tool is tagged with what Agent Builder LLM it would embed (e.g. “customer-service chatbot → Agent Builder LLM fine-tuned on support tickets”).
  7. Cognition preferences — client chooses default routing policy for the tools: local-only / Claude-welcome / hybrid / per-tool overrides.
  8. Human-in-loop prioritization — client picks top 3 (the Ensemble executes; we don’t barrel into 12 projects).

Build phase — for each picked tool:

  • Agent Builder sub-run — if the tool embeds a custom LLM, Agent Builder runs first to produce the .gguf or LoRA adapter.
  • Spawn a dedicated Agent with a charter for that tool.
  • Agent scaffolds from the Phase 2 reference stacks (§3.8).
  • AI layer wired in: the tool imports the router (§3.1.d), which routes across Tiers K/L/O/C per the client’s LLM_SPEC.md.
  • Tests + eval + deploy via Ensemble standard flow.
  • Setup experience for the client: Apple-product grade (Founding Principle §2). One-command install when possible. Pre-filled sample data. Readme that reads like a product manual, not an engineer’s note.

Artifact: BUSINESS_ROADMAP.md — updated quarterly; shows what’s built, what’s queued, what the current top 3 are, what metrics each tool is moving, what Agent Builder LLMs are live and when they last refreshed.

7. The autonomous-improvement loop

Kevin’s exact words: “feed the info back into claude to review, reorient and implement changes then the loop continues.”

This is the Ensemble’s overnight-autopilot pattern applied to the client product:

   Deployed tool
       │
       ▼
┌────────────────────────┐
│ Observability (Phoenix)│ ◄──── user interactions, model outputs,
│ captures traces        │       errors, latency, cost
└───────────┬────────────┘
            ▼
┌────────────────────────┐
│ Eval Agent          │ ──► reads last-7-days traces, identifies
│ (nightly cron)         │     regressions, categorizes errors
└───────────┬────────────┘
            ▼
┌────────────────────────┐
│ Re-orient Agent     │ ──► decides: prompt tweak? more RAG? 
│ (Claude Opus)          │     fine-tune refresh? alert human?
└───────────┬────────────┘
            ▼
┌────────────────────────┐
│ Implement Agent     │ ──► makes the change in a feature branch,
│ (scoped to tool repo)  │     runs eval set, opens PR with diff + 
│                        │     justification
└───────────┬────────────┘
            ▼
┌────────────────────────┐
│ Human approval gate    │ ◄──── Kevin (or client admin) approves
│ (review queue)         │       or rejects
└───────────┬────────────┘
            ▼
     Merge + redeploy
            │
            ▼
       (loop)

Key design choice: the improvement loop never ships to production without human approval. This aligns with safety_constraints.md — no auto-push, no auto-deploy. The loop produces a proposed change; a human decides.

9. Risks & unknowns

Risk Severity Mitigation
Anthropic changes Claude API terms or pricing in a way that breaks our per-client math High Cognition flexibility is the insurance (§3.1). Tiers K/L/O carry the essential path; Tier C is upgradable/replaceable. Test the Claude-disabled path end-to-end at every Phase exit.
Open-weight model quality plateaus; we can’t fine-tune well enough for client accuracy bars Medium Bias toward RAG + prompting over fine-tuning; reserve fine-tune for narrow-domain wins. Router can fall back to Tier C (opted-in clients) for hard tasks.
A regulated client needs compliance (HIPAA, SOC 2) we don’t have Medium Stay in Tier 3/4 until we have one deal worth the certification burden. Partner with an MSP who already has it for Tier 1/2.
The Ensemble doesn’t scale beyond Kevin — pattern breaks when there’s a team of humans, not just a solo dev Medium Watch for it at Phase 0 exit; design the multi-human handoff explicitly in Phase 3.
We try to build all three phases in parallel, dilute execution, ship none well High This doc’s phased gates. Each phase exits before the next begins. No parallel phase work.
Competing products (CrewAI, AutoGen, OpenDevin) eat our lunch Low-medium Our moat is the orchestration + the Apple-quality polish + the end-to-end pipeline from intake to deployed product. Frameworks don’t ship businesses; we do.
Privacy tier boundaries are violated in practice, not just in theory High Build the data-class enforcement hook at Agent Builder start (Phase 1), not as an afterthought. Red-team it. The router (§3.1.d) is the choke point; test it like the autopilot lock was tested.
The router becomes a bottleneck or single point of failure Medium Keep it tiny, stateless, horizontally scalable. Failure mode: fail-closed → degrade to Tier K only, never leak to lower privacy.
“Cognition flexibility” becomes “cognition chaos” — too many knobs, confusing for clients Medium The Agent Builder Interview (§5) collapses the choice to 4 preset profiles (“local only” / “Claude-welcome hybrid” / “cloud-first” / “custom”). Advanced clients can hand-edit LLM_SPEC.md; defaults handle 95%.
Quality bar slips in the rush to ship Phase 1 High Founding Principle §1. Every Phase exits on real-world use + 30-day operation, not on “feature complete.” Ugly is not ship-ready.
