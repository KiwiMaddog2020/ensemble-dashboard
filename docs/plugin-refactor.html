Plugin Refactor — The Ensemble as a Claude Code Plugin

Status: plan, 2026-04-22. Prereq: Track I publication research at research/track_i_publication.md. Target: The Ensemble publicly installable via /plugin install ensemble@claude-ensemble by flipping the repo public + adding two manifest files + path migration. Estimated 10–20 focused hours; 1–2 weeks calendar. Execution strategy: branch plugin-refactor; Kevin’s current install stays on main until cutover.

1. Why this refactor

The Ensemble today is a self-hosted bundle of scripts + templates under ~/.claude/orchestrator/. To be a Claude Code plugin (the only format distributable via marketplaces), we need:

  1. A .claude-plugin/plugin.json manifest naming the plugin ensemble (so skills surface as /ensemble:maestro and /ensemble:agent-onboard).
  2. A .claude-plugin/marketplace.json at repo root cataloguing the plugin.
  3. All file references using plugin-relative env vars (${CLAUDE_PLUGIN_ROOT} for read-only bundle, ${CLAUDE_PLUGIN_DATA} for writable state) instead of hardcoded /Users/kevin/....
  4. A public GitHub repo with LICENSE.
  5. Hooks registered via plugin.json (not the user’s ~/.claude/settings.json).
  6. launchd/ and scheduled-task integration migrated into the plugin’s own hooks/ + monitors/ where possible, or clearly documented for reviewers.

Post-refactor: anyone worldwide can run three commands and have a working Ensemble.

Why launchd/ stays at repo root, not in the plugin

The sweeper plist is a macOS user-agent that runs outside Claude Code. It’s an installer artifact — the user opts in by running launchctl load. Packaging it inside the plugin would blur the line between “plugin code” (runs in Claude Code) and “host-machine automation” (runs as a user agent). Reviewers flagged this as a scrutiny risk (Track I §7 gotcha). Keeping it at repo root, with INSTALL.md documenting the opt-in step, makes the boundary crisp.

4. Path-variable migration pass

Two env vars replace all hardcoded paths:

Path type Old (hardcoded) New
Plugin bundle (read-only) — scripts, templates, skills ~/.claude/orchestrator ${CLAUDE_PLUGIN_ROOT}
Plugin data (writable, per-user, survives updates) — state.json, work_hours.json, chats/, briefings/, queue/, pulse/, runs/, charters/, lock_steals.log, state.lock.d/ same hardcoded root ${CLAUDE_PLUGIN_DATA}

Scripts (12 files in plugins/ensemble/bin/)

Current pattern: ORCH="~/.claude/orchestrator". New pattern:

ORCH="${CLAUDE_PLUGIN_ROOT:-~/.claude/orchestrator}"        # for bundle files (templates, other scripts)
ORCH_DATA="${CLAUDE_PLUGIN_DATA:-$ORCH}"                              # for writable state — falls back to ORCH for legacy compat
STATE="$ORCH_DATA/state.json"
LOCK_DIR="$ORCH_DATA/state.lock.d"
LOG="$ORCH_DATA/lock_steals.log"
WORK_HOURS="$ORCH_DATA/work_hours.json"
CHATS_DIR="$ORCH_DATA/chats"
BRIEFINGS_DIR="$ORCH_DATA/briefings"
# etc.

The ${VAR:-default} pattern preserves backward-compat for the current self-hosted install on Kevin’s machine. Once the plugin is installed, Claude Code sets the env vars and the old paths stop being used.

Markdown files (templates, SKILL.md, bootstraps, CHEATSHEET, TROUBLESHOOTING, onboarding_prompt)

Current pattern: absolute paths in prose like Read ~/.claude/orchestrator/templates/AGENT.md.

New pattern: use ${CLAUDE_PLUGIN_ROOT} in prose and provide path resolution in-context. For SKILL.md files specifically, Claude Code’s agent will know how to resolve ${CLAUDE_PLUGIN_ROOT} because it’s the standard plugin env var.

Example (maestro/SKILL.md):

Read `${CLAUDE_PLUGIN_ROOT}/templates/MAESTRO.md` in full.
Read `${CLAUDE_PLUGIN_DATA}/state.json`.

        "matcher": "mcp__(computer-use|Claude_Preview|Claude_in_Chrome)__.*",

}

Hooks declared here are auto-registered when the plugin is installed — the user does not need to edit ~/.claude/settings.json. That’s the biggest UX win of plugin-form distribution.

7. Scheduled tasks — keep as optional post-install extension

The 4 Desktop scheduled tasks (morning-briefing, evening-planning, overnight-heavy, workday-pulse) + the launchd sweeper are not part of the plugin bundle. They are opt-in side effects the user enables after install. The plugin ships a command (/ensemble:enable-routines or a section in INSTALL.md) that walks through creating them via mcp__scheduled-tasks__create_scheduled_task calls pointing at ${CLAUDE_PLUGIN_ROOT}/bin/routine_prelude.sh.

Rationale (from Track I §7 gotcha): plugins that spawn persistent host processes invite reviewer scrutiny. By making routines an explicit post-install opt-in with user approval per-task, we keep the core plugin’s surface minimal — only hooks + skills — and the riskier automation is user-consented.

8. Kevin’s install migration

Two-stage cutover. Work happens on plugin-refactor branch; Kevin’s current install stays on main throughout.

Stage 1 — Branch work (no impact on current install)

  1. git checkout -b plugin-refactor
  2. Execute sections 3–6 of this plan (file moves, path sweep, manifests).
  3. CI passes on the branch.
  4. Branch is ready to cut over.

Stage 2 — Cutover (atomic, takes ~15 minutes)

  1. Backup first — run bin/backup_snapshot.sh on Kevin’s live install. Snapshot lands at backups/<YYYY-MM-DD>/.
  2. Merge plugin-refactor → main on GitHub.
  3. Install the plugin locally: /plugin marketplace add KiwiMaddog2020/claude-ensemble /plugin install ensemble@claude-ensemble
  4. Migrate state into ${CLAUDE_PLUGIN_DATA} via a one-shot migration script plugins/ensemble/bin/migrate-from-legacy.sh that: - Copies ~/.claude/orchestrator/state.json → ${CLAUDE_PLUGIN_DATA}/state.json - Copies chats/*.json, charters/*, briefings/*, queue/*, pulse/*, runs/*, lock_steals.log, work_hours.json → ${CLAUDE_PLUGIN_DATA}/... - Verifies: jq . ${CLAUDE_PLUGIN_DATA}/state.json passes.
  5. Update the 4 scheduled tasks — edit each task’s prompt to point at ${CLAUDE_PLUGIN_ROOT}/bin/routine_prelude.sh (via mcp__scheduled-tasks__update_scheduled_task). Or delete and recreate.
  6. Remove the old hook entries from ~/.claude/settings.json (the plugin now owns hooks).
  7. Verify: ~/.claude/orchestrator/bin/status.sh (if it still runs) OR the new /ensemble:status command reports all systems go.
  8. Archive old install — mv ~/.claude/orchestrator ~/.claude/orchestrator.legacy.<ts>.
  9. Dogfood for 24–48 hours. Anything breaks, rollback via mv + /plugin uninstall.

Stage 3 — Public flip

  1. Confirm 48 hours of clean dogfood post-cutover.
  2. GitHub → Settings → flip repo visibility to public.
  3. Add LICENSE + refresh README.
  4. Tweet/post the install command. The Ensemble is publicly installable.

12. Out of scope for this refactor

  • Official directory submission. That’s Phase 2 per Track I §6. After Phase 1 (this refactor) lands + 1 week of public availability, submit via the form.
  • “Anthropic Verified” badge. Discretionary; weeks-to-months. Not blocking anything.
  • Plugin-native monitors. Track I §7 suggests migrating launchd + scheduled-tasks to plugin-native monitors if the format supports them. Research confirmed plugin.json supports hooks and MCP servers; monitors as a built-in may or may not exist. Keep current opt-in model for v1.0, revisit for v1.1.
  • Multi-machine / Linux support. v1.0 is macOS only. Linux port is v2.
  • Migrating Kevin’s memory files into the plugin. They stay in ~/.claude/projects/-Users-kevin/memory/ — user-specific, not plugin content.

13. Success criteria

Phase 1 — this refactor — is done when:

  • ✅ Repo contains valid plugin.json + marketplace.json, passes claude plugin validate.
  • ✅ All Kevin-specific hardcoded paths removed from the plugin bundle.
  • ✅ Kevin’s install is running off the plugin-form (no ~/.claude/orchestrator in active use).
  • ✅ Hook + lock + routines all still work from plugin paths.
  • ✅ 48 hours of clean dogfood post-cutover.
  • ✅ Repo is public with LICENSE + README.
  • ✅ Another Claude Code user can run /plugin marketplace add + /plugin install and have a working Ensemble on a fresh machine.

When all six check, The Ensemble is publicly installable. Completion goes from ~60% → ~75%.

Phase 2 (official directory listing) takes completion to ~90%. “Anthropic Verified” takes it to 100%, but that’s not required for “fully published”.
